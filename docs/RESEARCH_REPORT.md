## 연구 개요

MLB 경기 데이터를 수집하고 머신러닝 모델과 LLM 네레이터를 개발했다. 통계 모델의 예측에 선수별 경기 내용을 읽는 분석을 더하면, 종합 지표만으로 설명하기 어려운 판단을 보완할 수 있는지 알아보고 싶었다. 예측을 실제 경기와 대조하면서 데이터 오류, 미래정보 누수, 근거를 읽고도 판단에 반영하지 못하는 문제를 추적했다.

수집 코드와 학습 노트북, 선수별 누적 기록, 경기별 추론, 결과 대조와 회고를 연결했다. 모델 정확도뿐 아니라 입력이 언제 만들어졌는지, 어떤 선수를 가리키는지, 같은 근거를 다시 읽었을 때 판단이 유지되는지도 조사했다. 이 보고서는 운영 단계를 마친 개인 연구·개발의 기록이다.

수치는 당시 저장된 실험 결과를 기준으로 제시한다. 평가 대상과 입력 조건이 다른 결과는 직접적인 성능 개선의 증거로 사용하지 않는다.

## 1. 경기 정보를 모아 GPT에 전달하는 작업부터 시작했다

2025년에는 GPT로 MLB 분석 지침을 수정하고 경기 결과를 기록하는 사전 시도를 했다. 당시 문서에는 분야별 가중치, 홈·원정 비교표, 경기 전 입력 시각과 단위 통일, 결과 피드백 절차가 있다. 문서에 적힌 목표 적중률과 실제 검증 성과는 구분했다.

2026년에 본격 개발을 진행했다. 초기에는 Claude 채팅에서 개발 방향과 코드를 논의하고, 코드를 Colab에 붙여 실행한 뒤 Google Drive에 결과를 보관했다. 현재 확보한 자료에서는 3월 20일의 경기 데이터와 GPT 프롬프트부터 이 과정을 추적할 수 있다. 3월 21일의 초기 운영 문서는 경기 전 수집 → 프롬프트 생성 → GPT에 입력 → 경기 후 결과 저장 순서를 설명한다. 대화가 바뀌면 요약 Markdown을 첨부해 작업을 이어갔다.

이후 과거 3시즌의 입력을 재구성하는 계산 엔진, CSV로 학습하는 모델, 일별 예측·결과 저장으로 확장했다. 일일 실행과 평가 과정에서 누수를 발견해 입력을 다시 설계했다. 그 뒤에는 선수별 근거를 읽는 네레이터와, 판단이 틀린 이유를 조사하는 회고 체계를 개발했다.

당시 파일의 이름을 따라 규칙 계산 엔진은 A안, CSV 기반 학습 모델은 B안, 운영용으로 선택한 학습 모델 버전은 종결 v1/v2로 구분한다. clean은 입력 시점과 특성 정의를 다시 정리한 후기 모델의 이름이다.

경기를 판단하려면 선발 성적 하나로는 부족했다. 경기 일정과 타순, 투수·타자 기록, 불펜 사용량, 구장과 날씨, 부상·출전 상태, 시장 기준점이 서로 다른 곳에 있었다. 첫 번째 과제는 이 자료를 같은 경기와 선수에 연결하는 것이었다.

초기 자료에는 프롬프트 생성 노트북과, 생성된 프롬프트를 파싱해 계산·백테스트하는 엔진이 따로 남아 있다. 계산 엔진은 선발, 불펜, 타선, 홈·원정, 상대전적에 점수를 매겼다. 이후의 학습 모델 및 LLM 네레이터와는 다른 초기 방식이다.

연구 질문도 진행하면서 달라졌다. 처음에는 어떤 자료와 계산으로 경기 방향을 판단할지 다뤘다. 모델과 LLM의 예측을 실제 경기와 대조하면서는 “경기 전에 볼 수 있었던 정보를 왜 판단에 반영하지 못했는가?”를 조사하게 됐다. 수집이 빠졌는지, 선수와 기록의 연결이 틀렸는지, 정보를 읽고도 잘못 판단했는지를 나눠 확인하기 시작했다.

초기에는 소수 경기의 결과가 나쁘다는 이유로 프롬프트 규칙을 바로 바꿀 것인지를 논의했다. GPT는 구조 수정을 제안했고 Claude는 소표본 변동을 구조적 결함으로 단정할 수 없다고 반박했다. 나는 Claude가 제안한 사전 태깅, 결과를 본 뒤 태그를 고치지 않기, 평가 기준을 먼저 고정하기를 채택했다. 이후 실험에서도 결과를 설명하는 규칙과 아직 보지 않은 경기에서 검증할 규칙을 구분하려 했다.

## 2. 수집한 자료의 결측, 중복, 단위를 고쳤다

아래는 여러 개발·실험 경로의 공통 흐름이다. 경기의 플레이별 기록을 PBP, 경기와 선수별 자료를 누적한 파일을 원장이라고 부른다.

```text
공식 API·웹 자료 수집
          ↓
경기·선수 ID로 연결하고 시점·단위·결측 점검
          ↓
경기 전 입력 고정
          ├─ 통계 모델: 승패 확률·예상 총득점
          └─ 네레이터: 선수별 양 팀 근거 비교
                      (모델 출력과 계산 근거도 참고)
          ↓
예측과 사용한 입력·근거를 함께 저장
          ↓ 경기 종료 후
실제 결과 및 원본 PBP와 대조·회고
          ↓ 사전정보와 사후 사건 분리
누적 기록 갱신 → 다음 경기 시점에 사용 가능한 입력
```

총득점 분석은 양 팀 점수 합계가 주어진 기준점보다 높은지 낮은지를 판단하는 과제다.

### 여러 출처를 역할별로 연결했다

공식 일정, 플레이별 경기 기록(PBP), 박스스코어를 경기와 선수별로 연결했다. 투구·타구 측정 자료인 Statcast에서는 공의 질을, 시장 자료에서는 승패 시장가격과 총득점 기준점을 가져왔다. 날씨, 구장, 심판 기록과 뉴스로 경기 환경과 출전 조건을 보완했다.

자료마다 수집 단위와 용도가 달랐다.

| 자료 | 출처와 수집 방식 | 연결한 용도 |
|---|---|---|
| 일정·박스스코어·PBP | MLB Stats API, 시즌·날짜·경기별 호출 | 경기 ID, 선수 ID, 타순, 투구·타석 사건, 결과 |
| 시범·정규·마이너 기록, 거래·IL | 공식 기록과 별도 수집기 | 시즌 유형과 콜업·부상·출전 상태 구분 |
| 투구·타구, 구장 지수 | Statcast/Savant의 원장·집계표, 구장 자료 | 구속·회전·접촉 질, 상대 조건과 환경 |
| 승패 시장가격·총득점 기준점 | The Odds API, Yahoo, OddsPortal, BetExplorer 관련 수집 코드 | 모델 입력, 시장 확률 비교, 총득점 기준선 |
| 날씨·심판·뉴스 | OpenWeatherMap, Open-Meteo, 공식 기록·발표 | 구장 조건과 경기 전 출전 맥락 |

제공처가 바뀌면서 요청 방식도 달라졌다. 시장가격 수집 노트북은 페이지 구조 조사, Selenium을 이용한 OddsPortal 경기 목록과 개별 경기 조회, 저장 결과 검증을 나눴다. 다른 수집기는 공식 팀 ID를 Yahoo 경기 ID에 연결했다. 출처 목록은 각 버전의 수집·구현 이력이며, 모든 출처가 매일 동시에 성공한 것은 아니다.

### 사례 A. 저장 행 수를 수집 성공으로 오해할 수 있었다

구형 라인업 수집 노트북에는 8경기 표를 저장했지만 총득점 기준점 시장값은 1경기에만 매칭됐다는 출력이 남아 있다. 다른 초기 프롬프트에는 기준점을 수동 입력하고 없으면 평균으로 대체하는 설정도 있었다.

8행을 저장했어도 8경기의 시장값을 확보한 것은 아니었다. 실제 수집값, 수동 입력값, 평균 대체값을 구분해야 이 결측을 찾을 수 있었다.

### 사례 B. 조인이 경기 수를 늘렸다

초기 2022 데이터 구축 출력에는 경기 2,431개가 선발자료 조인 뒤 2,481행으로 늘어난 기록이 있다. 이어지는 셀은 선발 자료의 중복 gamePk(MLB 공식 경기 ID)와 경기 결과 자체의 중복을 따로 조사했다. 정리 후 2021년 2,429행, 2022년 2,430행과 중복 0이라는 출력이 남았다.

경기 수가 늘어난 원인을 찾으려면 조인 전후 행 수와 중복 키를 함께 확인해야 했다.

별도의 마스터 구축 노트북은 2023~2025 경기결과, 시장가격, 선발, 타순 자료를 합치는 과정을 보여준다. 선발과 타선은 경기 ID로, 시장가격은 날짜와 양 팀 이름으로 연결했다. 저장 출력에는 최종 7,277행 중 시장가격 7,253행, 타선 7,276행이 매칭됐다고 남아 있다. 다만 경기결과 7,290행이 중복 제거 뒤 7,277행으로 줄어든 이유와 더블헤더 구분의 정확성은 이 출력만으로 확정할 수 없다.

더블헤더 게임번호를 별도로 수집한 노트북도 있었다. 날짜·점수 불일치 사례였던 경기 ID 718541, 718543, 718399는 공식 일정의 저장 출력에서 모두 더블헤더 2차전이었다. 같은 날짜에 같은 팀이 두 번 만나거나 순연된 경기는 날짜와 팀명만으로 구분하기 어렵다. 이 대조는 식별 문제를 조사할 단서를 제공했지만, 개별 불일치의 원인을 모두 확정한 것은 아니다.

### 과거 경기 입력을 재구성하며 시즌 선택도 점검했다

같은 노트북에는 과거 프롬프트를 점검한 코드와 출력이 남아 있다. 한글 파일명 패턴으로는 파일을 찾지 못했지만 디렉터리 목록을 직접 조회해 텍스트 181개를 확인했다. 이어 정규시즌 중인 투수에게 시범경기 최근 등판이 먼저 선택되는 문제를 조사하고, 해당 경기일 이전의 정규시즌 등판과 비교했다. 후속 생성기에서 이 문제가 모두 고쳐졌는지는 확인하지 않았다.

### 사례 C. 불펜 집계 범위와 구장 지표의 단위를 맞췄다

불펜 사용량은 홈·원정 일부 이력만 보는 계산과 팀의 모든 경기 이력을 보는 계산 사이에 차이가 있었다. 구장 지표는 일부 시즌에서 중립값을 약 1로, 다른 시즌에서는 약 100으로 다루었다. 수정 기록에는 불펜 집계를 다시 만들고 구장 스케일을 맞춘 과정이 남아 있다.

B안 피처 요약에는 최근 5·10경기 이동 집계, 과거 맞대결, 선발을 제외한 불펜 이닝, 주심 누적 기록, 부상자 명단(IL) 증감의 정의와 결측이 적혀 있다. 선발 ID가 없어 이름으로 연결한 경우와 음수 IL 값도 기록돼 있다.

### 수집 방법 자체도 검증했다

Savant 수집 지시와 당시 검증 보고서를 대조했다. 검증 문서에는 CSV 응답 한도, 잘못된 API 주소와 연도 필터, HTML 내 JSON 추출, 일별 분할 수집으로의 수정이 기록돼 있다. 구형 수집기는 연도별 순위·집계표(leaderboard) 4종을 받아 선수 ID와 이름으로 합쳤다.

연간 집계표와 투구별 원장은 포함하는 기록과 집계 단위가 달라 따로 구분했다.

### 경기 후 갱신이 경기 전 자료를 지우지 않게 했다

초기 로컬 파이프라인은 수집기, 예측기, 결과 갱신기로 나뉘었다. 두 갱신기 버전을 비교하면 시장가격 저장을 제거한 변경이 보인다. 경기 종료 후 Yahoo가 비어 있는 시장가격을 반환할 때, 그 값이 경기 전 수집한 정상 시장가격을 덮어쓰는 문제를 막기 위한 수정이었다. 중복 처리도 단일 키에서 복합 키를 받을 수 있도록 확장했다.

다만 당시 날짜·홈팀 복합 키로는 같은 날 같은 홈팀의 두 경기를 구분할 수 없었다.

## 3. 계산 규칙과 학습 모델을 비교했다

### A안에서 무엇을 시험했나

로컬의 A안 결과 문서는 프롬프트를 파싱하는 계산 엔진을 설명한다. 선발, 불펜, 타선, 구장, 상대전적의 기여를 정해진 식으로 합하고, 가중치와 선택 기준을 바꿔 결과를 비교했다.

A안은 시장가격 없이 기록만으로 예측하도록 설계했다. 이후 엔진의 출력과 시장가격에서 환산한 확률을 서로 다른 비율로 섞어 비교했다. 원문에 나온 “최적”이나 “천장”은 여러 조건과 서로 다른 경기 표본을 탐색한 결과에 붙인 표현이므로 일반적인 성능 한계로 해석하지 않았다.

2023~2025년의 경기 전 입력을 다시 만들기 위해 연도별 생성기를 작성했다. 선발의 최근 등판, 타자 폼, 불펜 사용, 날씨, IL과 시장 기준선을 경기별 프롬프트로 묶었다. Colab 실행 래퍼와 로컬 생성기 본체, 날짜별 저장 출력이 함께 남아 있다. 입력 재구성 과정에서는 시즌이 고정되거나 정규시즌보다 시범경기 기록이 먼저 선택되는 문제도 조사했다.

계산 엔진의 지표를 선택할 때는 해당 지표가 유리한 집단과 불리한 집단의 결과 차이를 비교했다. 구장·홈원정 ERA와 좌우 조건을 채택하고 피배럴률이나 최근 30일 ERA를 제외한 판단 기록이 있다. 이후 가중치 탐색에서는 구장별 ERA 가중치가 기본 0.30에서 0으로 선택됐고, 홈·원정 가중치는 0.20에서 0.40으로 바뀌었다.

### B안에서 무엇을 바꿨나

B안은 CSV 자료로 학습한 모델이었다. 결측값, 변수 간 상관과 다중공선성(VIF)을 검사하고 입력 특성을 구성했다. Logistic Regression, XGBoost, LightGBM을 비교한 노트북이 남아 있다. 정확도 외에 AUC와 Brier score로 분류·확률 예측을 평가하고, 확신도에 따른 선택 건수와 월별 결과도 확인했다.

저장된 모델 설정은 다음과 같다. LR은 Logistic Regression, LGB는 LightGBM이다.

| 버전 | 승패 | 총득점 기준점 위·아래 분류 |
|---|---|---|
| B안 |24개 특성, LR60%+LGB40%|25개 특성, LR80%+LGB20%|
| 종결 v1 |15개 특성, LR80%+LGB20%|25개 특성, LR50%+LGB50%|
| 종결 v2 |12개 특성, LR80%+LGB20%|22개 특성, LR50%+LGB50%|

계산 엔진의 v1~v3와 학습 모델의 종결 v1/v2는 별도로 관리한 버전이다. 4월에는 Statcast 특성을 추가해 16/25개 특성을 사용하는 별도 시험(shadow) 계획도 작성했다. 이는 이후 202/190개 특성을 사용한 clean 모델과 다른 작업이며, 계획대로 실험을 완료했는지는 확인되지 않았다.

### 파라미터를 탐색하고 별도 검증 기록과 대조했다

그리드서치 코드는 LR 정규화 강도, LightGBM의 잎 수와 깊이, 최소 학습 표본, 두 모델의 혼합비를 바꿨다. 2021년으로 2022년을 평가하는 방식부터 2021~2024년으로 2025년을 평가하는 방식까지 네 구간을 사용했다. 저장된 CSV에는 승패 2,880조합과 총득점 2,400조합의 결과가 있다. 각 조합에서 선택 임계값별 정확도와 경기 수, 시즌별 최저 성적과 편차를 비교했다.

종결 v1 보고서는 두 종류가 남아 있다. 한 보고서의 선택 경기 수와 소수 첫째 자리 성적은 탐색 CSV의 같은 설정 행과 일치한다. 반면 별도로 보관된 보고서는 선택 경기 수와 성적이 다르다. 두 보고서의 차이를 설명하려면 입력 표본, 결측 처리, 평가 구현을 대조해야 한다. 탐색 최고값을 그대로 최종 모델 성과로 옮겨 적거나, 후보 선택에 사용한 네 평가 구간을 독립적인 최종 시험으로 간주하지 않았다.

v2에서도 같은 이름의 학습 자료를 구분해야 했다. 저장 출력이 있는 재학습 노트북은 심판 관련 특성 두 개와 기온을 제거해 12/22개 특성을 사용한다. LR과 LightGBM 모두 유효 학습행 전체를 사용하며, 종결 v2 모델 네 개의 저장 출력과 설정 JSON에 대응하는 평가 결과가 남아 있다. 별도의 로컬 학습 노트북은 LightGBM 학습행 일부를 검증용으로 남기는 다른 설계이고 저장 출력은 없다. 이 로컬 사본의 설계를 종결 v2 모델 전체의 학습 방식으로 설명하지 않는다.

### 비교표를 읽을 때도 조건을 확인했다

초기 노트북의 총득점 비교에서는 LR·LGB 앙상블을 사용한 셀 뒤에 LGB 단독 결과가 나온다. 마지막 표에 이를 과거 결과와 나란히 적었다고 동일 모델의 일반화 성능이 향상됐다고 읽을 수는 없다. 모델 구성과 선택 경기 수가 달랐다.

모델 구성과 평가 대상이 다른 초기 적중률은 대표 성과에서 제외했다.

### 일별 실행과 추가 지표 연구

종결 모델을 이용한 일별 수집·예측·결과 저장 코드와 운영 매뉴얼을 만들고, Colab 실행을 로컬 Python과 Drive 동기화 경로로 옮기는 작업도 진행했다. 일별 예측 원장은 실험 당시의 입력·출력·결과를 추적하는 자료로 사용했다.

추가 도메인 연구에서는 선수 split, 상대 팀 기록, IL, Statcast, 타순 좌우 구성과 시장 이동을 비교했다. 후보를 수집하고 조건을 바꿔 평가했지만, 일부 저장 성적은 전체 자료에 적합한 모델의 예측 위에서 계산돼 독립적인 미래 성능으로 사용할 수 없었다. 도메인을 확장한 구현과 그 효과의 입증을 분리해 기록했다.

## 4. 평가를 통과해도 데이터 시점은 틀릴 수 있었다

### 초기 홈승 v2에서 확인한 입력 문제

3월 말의 별도 홈승 모델 노트북은 3개년 자료, 세 모델과 확률 보정을 시험했다. 이 노트북의 `v2`는 앞 절의 종결 v2와 다른 버전명이다.

코드를 대조하니 같은 경기 ID의 타자 기록에서 출루율과 장타율의 합인 OPS를 평균해 승패 입력에 넣었고, 구장 평균 득점도 해당 시즌 전체 결과로 계산했다. 이 값은 경기 전에 확보할 수 있는 입력과 다르다. 결과 그림의 높은 AUC만으로 성공을 판단할 수 없는 이유였다. 당시 그 문제를 인지했는지, 각 특성이 성적을 얼마나 높였는지는 확인되지 않았다.

별도의 3월 31일 노트북에는 타자·투수 누적값에 직전 기록까지만 집계하도록 한 행을 늦추는 `shift(1)`을 적용하고, 이전 시즌의 기대 평균자책점(xERA)을 붙이는 코드가 있다. 두 구현의 차이는 확인했지만, 앞선 그림이 이 수정의 직접 계기였다고 단정하지 않는다. 후속 코드에도 실제 등장 선수로 집합을 정하거나 시즌 전체 구장 평균을 쓰는 문제가 남아 있었다.

### 일일 운영 모델에서도 누적값을 다시 점검했다

초기 모델은 기간을 나눠 평가했지만, 투수의 누적 비율 지표에 예측 대상 경기의 결과가 포함된 문제가 나중에 발견됐다. 학습·평가 기간을 나눴어도 입력값에 당일 결과가 섞이면 미래정보 누수가 생겼다.

당시 기록에는 누수를 의심한 과정도 남아 있다. 2026-05-27 메모는 ERA 차이 하나의 분류 성능이 높게 나온 것을 계기로 운영v2 입력을 조사하고, Sonny Gray의 경기별 행을 추적해 당일 결과가 누적 ERA에 반영되는 문제를 발견했다고 설명한다. 성능이 높다는 사실 자체가 누수의 증거는 아니다. 확인해야 할 것은 그 경기의 결과가 경기 전 입력값에 들어갔는지였다.

당일 결과를 포함하는 누적값을 경기 이전 기록으로 계산한 값과 구분했다. 실제 평균자책점(ERA)과 대용 지표, 시즌 누적과 통산 누적을 구별하고 학습·운영의 정의를 맞추는 작업을 진행했다. 이후 clean 모델에서는 승패를 LR·LGB 앙상블에서 단일 LightGBM 분류로, 총득점을 이항분류에서 총득점 회귀로 바꿨다. 저장 메타데이터에는 각각 202개·190개 특성과 학습 표본 12,149경기가 기록돼 있다.

구형 모델을 읽는 코드와 추천 여부를 참조하는 보조 코드도 남아 있어 모든 경로의 시점 검증을 완료했다고 볼 수는 없다. 탐색 과정에서 계산한 누수 비율은 조건이 충분히 확인되지 않아 대표 수치에서 제외했다.

### 시장 정보에도 시점이 있었다

저장된 승패 입력 특성에는 최초 시장가격뿐 아니라 마감 시장가격과 변화량을 포함한 구성도 있다. 이 구성의 결과를 최초 시장가격 시점의 예측 성과로 사용할 수는 없다.

승패 코드는 양 팀 시장가격에서 환산한 확률을 정규화한 뒤 모델 확률과의 차이를 계산한다. 총득점은 예측 총득점에서 기준점과 편향 보정값(bias)을 뺀 점수 차이로 방향을 정한다. 이 값은 확률이 아니다. 시장 정보가 모델 입력에도 포함되므로 모델과 시장의 같은 결론을 독립적인 두 근거로 세지 않았다.

## 5. 선수별 근거를 비교하는 LLM 네레이터를 개발했다

네레이터는 경기 전에 확보한 선수별 자료를 읽고 양 팀의 우위와 반론을 비교하도록 만든 LLM 분석 구성요소다. 모델의 예측값과 함께 그 근거를 참고하되, 개별 선수의 경기 내용까지 읽고 별도로 판단하게 했다.

예를 들어 선발의 시즌 ERA가 좋더라도 특정 구종·코스에서 최근 어떤 타구를 허용했는지, 상대 타자들이 그 조건에서 어떤 반응을 보였는지 살폈다. 불펜은 개별 투수의 사용량과 휴식, 역할을 연결했다. 확정 타순·선발과 달리 불펜 등판은 조건부 예상이므로 반드시 등장할 선수처럼 다루지 않았다.

공식 투구·타석 기록과 시점이 확인된 뉴스로 경기 내용을 읽게 했다. 영상을 직접 관찰한 것은 아니므로 자료에 없는 몸 상태나 동작의 원인을 추정해 쓰지 않도록 했다.

### 선수별 기록을 상대 조건에 연결했다

선수 ID를 중심으로 시즌과 최근 기간의 투구·타구를 묶고, 상대 좌우, 구종, 존, 직접 맞대결을 구분했다. 직접 상대했던 기록과 비슷한 조건의 다른 상대를 만난 기록은 따로 표시했다. 선발 두 명과 상대 확정 타순의 비교를 먼저 만들고, 벤치와 불펜은 가능한 투입 상황을 별도로 검토했다.

타석 도중 교체에서는 실제 공을 던진 선수와 공식 결과가 기록되는 선수가 다를 수 있었다. 이를 처리하기 위해 교체 이벤트와 박스스코어를 대조하고, 투구 물리 지표와 공식 타석(PA)·볼넷(BB)·삼진(K) 집계를 분리했다. 회전축의 각도 평균, 결측값, 미측정 스윙 자료의 분모도 별도 계약으로 정의했다. 원본 컬럼을 보관하는 것과 분석에 사용하는 집계값을 구분한 작업이다.

### 불펜은 예상 등판과 실제 등판을 나눴다

원본 PBP에서 투수별 등판 구간과 사용량을 만들고, 목표일 이전 기록으로 최근 투구 부담과 연투를 계산했다. 여기에 투수 역할과 휴식을 연결해 접전 후반, 마무리, 중간 연결, 긴 이닝을 맡길 후보를 제시했다. 이후 실제 등판과 비교하는 검증도 만들었다.

가용한 선수가 반드시 등판하는 것은 아니다. 팀 전체 피로가 높아도 핵심 구원투수가 쉬었을 수 있고, 특정 투수가 실제로 나와 잘 던졌다는 결과를 사전 예상에 넣을 수도 없다. 이 때문에 팀 요약과 개별 선수의 조건을 함께 유지했다. 예상 등판의 재현율과 경기 예측 개선 효과도 다른 지표로 다뤘다.

### 분야별로 근거를 읽고 반론을 남겼다

선수·분야별 근거를 연결한 뒤 양 팀의 우위와 위험, 반론을 비교했다. 승패와 총득점 판단은 따로 기록하고, 근거 참조와 누락 여부를 검사했다. 경기 종료 후에는 이 판단을 원본 PBP와 대조했다.

모든 자료를 긴 프롬프트에 넣는 방식부터 분야별 카드와 요약, 경기별 분리, 섹션별 메모까지 시험했다. 반대 근거를 반드시 쓰도록 출력 규칙도 바꿨다. 어느 방식도 모든 판단 오류를 해결하지는 못했다.

### 사례 D. 반대 근거를 필수로 쓰게 한 실험

6월에는 반대 근거를 명시하도록 하는 실험을 했다. 필수 항목을 작성했는지 보는 검사는 통과했지만, 모델 근거 검토 규칙(model-defense) 검사는 실패했다. 저장된 결과는 다음과 같다.

| 지표 | 이전 산출물 | 재분석 산출물 |
|---|---:|---:|
| 승패 적중/선택 |1/4|7/12|
| 총득점 적중/선택 |3/4|4/9|
| 회고의 오판 라벨 집계 |2|5|
| 회고의 정보 묻힘 라벨 집계 |2|3|

승패 적중률은 높아졌지만 총득점 적중률은 낮아졌고, 회고에서 오판이나 정보 묻힘으로 분류한 수는 늘었다. 선택 건수와 평가 대상이 달라 개선 효과를 단정할 수 없다. 회고 라벨도 원인을 확정하는 증거는 아니다. 이 실험에서 확인한 것은 필수 항목 작성 여부였고, 정보 누락과 판단 오류의 해결 여부는 남았다.

다른 점검에서는 요약 카드가 프롬프트에 전달되지 않았을 가능성을 조사했다. 확인한 날짜에서는 핵심 카드의 요약 누락을 찾지 못했다. 다른 날짜와 모든 세부정보까지 확인한 결과는 아니다.

이후 점검 과제를 자료 전달, LLM의 실제 열람, 의미 해석, 최종 판단 반영으로 나눴다. 각 단계를 확인해야 정보 누락과 판단 오류를 구분할 수 있었다.

## 6. 경기 후 회고도 다시 검증해야 했다

회고에서는 승리·패배와 총득점 증가·억제의 이유를 원본 PBP·박스스코어와 선수별 사건으로 연결했다. 맞은 경기와 틀린 경기, 모델과 네레이터가 갈린 경우를 모두 남겼다.

문제는 결과를 알고 쓰는 설명이었다. 경기 전에 위험 정보가 존재했다는 사실만으로 그 경기의 결과를 반드시 맞힐 수 있었다고 말할 수 없다. 사전 맥락의 존재와 실제 판단 누락을 구분하고, 경기 후에만 확인 가능한 사건이 다음 경기의 사전 근거로 잘못 들어가지 않도록 별도 검토를 만들었다.

초기 정독에서는 사전에 알 수 있었던 정보, 경기 후에만 확인된 사건, 우연·변동성 요인을 나눴다. 이후 검토 질문, 여러 시즌 정독, 제공된 근거만 사용하는 재정독, 선수별 누적 기록, 회고에서 추출한 판단기준으로 작업을 확장했다. 경기 집합별 재정독과 시즌 확장은 검토 대상과 목적이 다른 작업으로 구분했다. 같은 경기의 반복 검토를 독립 표본으로 합산하지 않았다.

승패와 총득점의 회고도 분리했다. 승패에서는 어느 팀의 득점·억제 경로가 상대를 앞섰는지, 총득점에서는 양 팀이 총점에 어떻게 기여했고 어떤 구간이 득점을 막거나 늘렸는지 보려 했다. 틀린 경기만 모으면 위험 신호만 쌓이므로 맞은 경기의 지지 근거와 모델이 맞고 네레이터가 틀린 경우도 같은 흐름에 포함했다. 회고 원장에서 검색용 라벨과 선수별 누적 카드를 만들되, 원문과 참조를 보존했다.

### 사례 E. 예측 당시 모델 입력을 따로 보존했다

모델이 맞고 네레이터가 틀린 경우를 조사하려면 당시 모델 입력을 알아야 했다. 그러나 최종 CSV에는 입력 고정 후 병합하거나 보강한 값이 들어갈 수 있었다. 나중에 그 CSV로 모델 기여도를 계산하면 예측 당시와 다른 입력을 설명할 수 있었다.

예측 직후 사용한 입력값, 모델 정보, 해시, 변수별 기여도를 별도 파일에 저장하도록 수정했다. 과거 자료에서 재구성한 기록은 ‘사후 재구성본’, 예측 당시 저장한 기록은 ‘예측 시점 저장본’으로 구분했다. 변수별 기여도는 모델이 어떻게 계산했는지에 대한 설명이며, 실제 경기 결과의 원인을 증명하지는 않는다.

### 사례 F. 검색한 기준을 당일 조건에 대조했다

PBP 회고에서 조건·반대 근거·무효화 조건을 추출하고, 당일 사전정보와 맞는 기준을 검색하는 구조를 연구했다. 선수·팀 이름이 다른 경기로도 가져갈 수 있도록 역할 중심으로 표현하는 시도도 있었다.

비슷한 기준을 찾아도 당일 경기에서 그 조건이 충족되는지 따로 판단해야 했다. 검색 점수를 최종 선택의 우선순위로 사용하거나, 선수별 근거보다 팀 종합지표를 과대평가하는 문제가 남았다. 이후 각 기준이 당일 경기에도 적용되는지, 반대 근거 때문에 약해지거나 무효가 되는지를 기록하고 양 팀이 이길 수 있는 과정을 비교하는 방안을 논의했다.

어떤 경기의 결과에서 만든 가설은 그 경기 자체로 검증하지 않도록 연구와 운영 적용을 분리했다. 저장한 기준의 수와 파일 형식 검사 통과 여부는 새 경기의 예측 성능과 따로 기록했다.

### 판단 일관성과 보류도 별도로 시험했다

최종 판정 연구에서는 같은 근거를 받은 판단자가 어디에서 갈리는지 검사했다. 판정 일치도 실험에서는 고정 사례 5경기를 대상으로 허용 파일만 읽는 격리 환경에서 24회 추론을 실행했다. 해당 실행의 참조 검사에서는 자기 경기 사례와 미래 정보의 잘못된 참조가 각각 0건이었지만, 방향을 정할 만큼 근거가 충분한지에 대한 판정은 일치도 기준을 통과하지 못했다.

판정 충분성과 경기 결과를 설명하는 메커니즘의 강도를 나눠 평가했다. 아래 Cohen's kappa는 우연히 일치할 가능성을 보정한 판단자 간 일치도이며, 경기 예측 적중률과는 다르다.

| 연구 | 저장 결과 | 이후 판단 |
|---|---|---|
| 판정 일치도 | 판정 충분성: 일치 70%, kappa 0.524로 기준 미달. 메커니즘 강도: 80%, 0.762로 통과 | 결합 검사 실패로 96경기 비교 차단. 확정 방향과 판단 불충분의 경계를 다시 조사 |
| 근거 처리 검사 | 20경기에서 1,419항목의 처리 누락·중복 0. 승패 20/20, 총득점 19/20이 보류 | 근거 처리 조건을 통과해도 거의 모든 후보가 보류되는 문제 확인 |
| 방향과 보류 분리 | 구현·계약 검토 완료. 고정 승격 평가의 선택 표본은 승패 2건, 총득점 1건이며 통계 기준 미달 | 운영 적용을 보류했고 이후 연구 단계에서 종료 |

방향·보류 분리 실험에서는 LLM의 방향 판단과 후처리의 유지·보류 판단을 분리했다. 같은 입력에서 비교할 방법과 평가 표본을 고정하고, 후처리가 후보 방향을 바꾸지 못하도록 했다. 코드 계약을 통과해도 적은 선택 표본으로 실용 성능을 입증할 수는 없었다. 선택 건수를 줄인 효과와 방향 판단이 개선된 효과를 따로 평가해야 했다.

## 7. 에이전트 분업과 비용을 함께 시험했다

### 같은 실험을 다시 실행할 수 있게 했다

MLB 경기는 시작 시간이 달라 하루 전체를 같은 시각에 처리하기 어려웠다. 일정 API로 시간을 묶고 라인업 등 입력의 준비 상태를 확인한 뒤, 준비된 경기만 처리하는 구조를 개발했다. 이미 입력을 고정한 경기는 건너뛰고 나머지는 해당 시간대에 재확인하도록 했다. 일정 기반 실행, 주기적 확인, Windows 예약 작업과 앱 자동화는 서로 다른 시도의 이력으로 남겼다.

경기 후에는 새로 종료된 경기만 결과와 회고에 추가하고, 누적 자료는 다음 목표일보다 이전 기록만 사용하도록 설계했다. 동결 입력의 해시, 경기별 출력 파일, 중복 실행 잠금, 실패 경기만의 재처리도 연결했다. 자동화 설정 파일의 존재와 실제 실행 완료는 별도로 확인했다.

Claude와 Codex의 공동 작업에서는 설계 제안, 반박, 검증 결과와 보류 결정을 해당 산출물에 연결했다. 실행 주체와 독립 검토를 나누는 브릿지, 대량 기준 추출을 위한 ChatGPT/MCP의 작업 할당·제출·검수 흐름도 시험했다. 생성 결과를 받았다는 사실만으로 품질 검수를 통과한 것으로 처리하지 않았다.

에이전트를 나눠 분석하자 같은 입력과 읽기 작업이 반복되면서 시간, 토큰, 로컬 메모리 부담이 커졌다. 자료를 다시 탐색하는 비용을 측정하고, 분업할 때 공유할 자료와 고정할 입력을 시험했다.

### 사례 G. 메인 세션과 별도 에이전트의 판단을 비교했다

에이전트 실행 방식 비교에서는 같은 10개 사전정보 섹션을 메인 세션과 하나의 지속 에이전트가 각각 읽었다. 최초 한 경기에서는 두 결과가 같은 방향이었고 섹션별 판단은 9/10 일치했다. 각자의 출력과 검증 결과를 고정한 뒤 경기 결과를 확인했다.

이 기록의 토큰 값 일부는 파일 크기를 4로 나눈 근사치로, 실제 계측값은 아니다. 후속 5경기의 승패 예측은 2경기 적중, 3경기 실패였다. 보수적인 조건을 추가하자 틀린 사례뿐 아니라 맞았던 사례도 선택에서 빠졌다. 결과를 확인한 뒤 조건을 바꾼 실험이므로 결과를 모르는 상태의 예측 성능으로 제시하지 않았다.

### 사례 H. 토큰 사용량을 한 경기 단위로 분해했다

후기 정독에서는 최종 답변 길이에 비해 사용량이 큰 원인을 살폈다. 입력, 캐시, 출력, 명령 호출을 나눠 보니 파일 재탐색, 출력 잘림, 명령 실패와 반복 문맥이 함께 작용했다.

경기 흐름과 사전자료를 한 번에 준비하고, 중복 내용은 참조로 연결한 입력을 시험했다. 원본 기록(RAW)과 박스스코어(BOX) 중 어떤 부분을 확인할지도 명시했다. 한 경기에서 측정한 값은 다음과 같다.

| 항목 | 이전 실행 | 개선 입력 실행 |
|---|---:|---:|
| 시간 |530.06초|300.05초|
| 파일·명령 호출 |20|0|
| 캐시 제외 입력 토큰 |155,256|149,359|
| 출력 토큰 |24,863|15,626|

시간은 43.4%, 출력 토큰은 37.2% 줄었지만 캐시 제외 입력 감소는 3.8%였다. 이 수치가 요금이나 구독 한도의 같은 비율 절감을 뜻하지는 않는다. 모든 원본 필드를 동일하게 전달한 비교가 아니어서 품질이 그대로 유지됐다고 단정할 수도 없다. 이전 투수가 남긴 주자의 실점을 요약한 문장이 모호한 문제도 발견해 별도로 정정했다.

### 무거운 처리는 Colab으로 옮겨 비교했다

Colab과 Drive API로 무거운 데이터 처리를 옮겼다. 로컬과 원격의 입력·출력 비교, 파일 해시와 크기 검사, 결과 회수, 세션 정리를 구현했다. 원격 실행에 성공해도 LLM 판단 품질은 별도로 검증해야 했다. Colab에서도 LLM 토큰 사용량은 발생했다.

같은 고정 입력을 사용한 모델 기초 단계에서 출력 비교를 통과한 실행이 있었지만, 후속 시간 측정 실행에서는 같은 단계의 필수 출력 세 개에 차이가 남았다. 두 실행의 입력 스냅샷도 서로 달랐다. 단계별 비교 성공을 네레이터까지 포함한 전 구간 동등성으로 확대하지 않았다.

## 8. 연구 결과와 남긴 한계

프로젝트에는 수집기와 데이터 마스터, 계산 엔진과 학습 모델, 선수별 근거 카드, 네레이터 입력, 추론, 검사 도구, 결과 대조와 회고, 실험 격리·비용 측정 코드가 남았다. 초기 코드부터 후기 연구까지는 작업 이력 부록에서 연결할 수 있다.

구체적으로 확인한 성과는 중복 조인과 단위·귀속 문제의 추적, 경기 전 시장가격 보존, 모델 입력 스냅샷, 경기별 실패 격리와 증분 갱신, 원격 처리 비교, 한 경기 정독의 시간·출력 토큰 감소다. 어느 하나를 시즌 전체 예측 정확도의 향상으로 바꿔 말하지 않는다.

충돌하는 근거 중 무엇을 우선할지, LLM 판단을 얼마나 일관되게 유지할지, 회고에서 만든 기준이 새 경기에도 통할지는 해결을 입증하지 못했다. 최신 세부자료 직접 검토 경로는 기존 경기별 자동 추론 경로와 분리된 채 남았다. 이 기록으로 모든 사전정보를 활용하면 모든 경기를 맞힐 수 있다거나, 네레이터가 모델보다 항상 우수하다고 주장할 수는 없다.

## 9. 내가 맡은 판단과 AI 활용

나는 자료를 더 모으는 일과 판단 방식을 바꾸는 일을 구분하며 연구 방향을 결정했다. 하루 회고에 의존하지 않고 정규시즌 누적 정보를 계속 갱신하도록 요구했고, 틀린 경기뿐 아니라 맞은 경기와 모델·네레이터가 갈린 경기도 회고 범위에 넣었다. 선수별 기록을 누적으로 갱신하고 양 팀의 근거를 나란히 보자는 요구도 이 과정에서 나왔다.

8월에는 다음 날 분석을 바로 시작하기 전에 이미 종료된 8월 12일 경기로 전 구간 리허설을 하도록 했다. 개발 기록에는 라인업의 Python 리스트 표현을 단순 쉼표 문자열로 읽어 선수 이름을 잘못 인식하는 파서 결함을 발견하고, 입력 형식별 회귀검사로 수정한 과정이 남아 있다. 리허설은 다음 실행의 입력·출력 연결을 확인하려는 것이었다.

Claude와 Codex는 코드 구현, 분석, 검토와 설계 제안을 지원했다. 평가 원칙처럼 AI가 제안한 내용을 채택한 경우와, 내가 연구 목표·검증 범위·실행 순서를 바꾼 경우를 구분했다. 문제 정의와 실험 방향, 최종 채택 여부는 내가 결정했고 코드 작성과 검토에는 AI의 도움을 받았다.

최종적으로 운영을 계속 복구하기보다 연구·개발 기록으로 마감하기로 결정했다. 통계 기준을 통과하지 못한 후기 판정 방법은 운영에 승격하지 않았다. 이 문서는 데이터 수집부터 모델과 LLM 분석, 결과 대조까지의 연구 기록을 제공한다. 원천 데이터와 모델 가중치, 인증정보는 배포하지 않는다.

## 자료 출처와 평가 범위

| 출처 | 연구에서 다룬 자료와 용도 |
|---|---|
| MLB Stats API | 일정, 경기 ID와 선수 ID, 박스스코어, 플레이별 기록, 시즌 유형과 선수 기록 |
| Baseball Savant / Statcast | 투구·타구 측정치, 연도별 집계표와 구장 관련 지표 |
| The Odds API, Yahoo Sports, OddsPortal, BetExplorer | 버전별 수집·구현 과정에서 다룬 시장가격(배당)과 총득점 기준선 |
| OpenWeatherMap, Open-Meteo | 날씨 수집과 결측 보완 |
| 공식 발표·경기 기록·뉴스 | 출전 상태, 거래·부상, 심판과 경기 전 맥락 |

출처마다 조회 방식과 집계 단위, 당시 확보한 범위가 달랐다. Google Drive와 Colab은 저장·실행 환경이며 데이터의 원 제공처가 아니다.

보고서의 실험 수치는 보존된 학습 메타데이터, 평가 출력과 실행 기록을 바탕으로 정리했다. 저장소에는 [선정한 코드·노트북 발췌본](../src/README.md)도 포함한다. 시장가격 수집·송신·금액 기능과 비공개 자료를 제외한 정리본이므로 운영 당시 코드와 동일하지 않다. 전체 학습·추론 환경, 일부 의존 모듈과 원천 데이터가 빠져 있어 같은 성적을 바로 재현하는 실행 패키지는 아니다. [변경표](CODE_CHANGELOG.md)에 정리 범위와 정적 검수 한계를 남겼다.
